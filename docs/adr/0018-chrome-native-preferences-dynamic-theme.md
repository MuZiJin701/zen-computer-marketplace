# ADR 0018: Chrome native `Preferences` dynamic theme (`Seed-driven native theme`)

## Status

Accepted — 2026-11-24; supersedes the Chrome manual dual-MV3-extension clauses of [ADR 0006](0006-mode-coherence-and-system-following.md) and [ADR 0010](0010-evidence-backed-appearance-policy.md); extends `Live-process write guard` from [ADR 0016](0016-matlab-desktop-mlsettings-target.md).

## Context

Previously, One-Tone generated two static Manifest V3 theme extension packages (`one-tone-<plan>-light` and `one-tone-<plan>-dark`) for Chrome and required manual loading and manual mode switching in `chrome://extensions`. Inspection of Chromium's `ThemeHandler` / `BrowserThemePack` manifest parser and WECG extension APIs confirmed that static Chrome `"theme"` manifests accept only one color table without `prefers-color-scheme` branching, and Chrome exposes no `chrome.theme.update()` API for runtime theme switching.

Controlled read-only inspections and four rounds of offline write/restart experiments against Windows Google Chrome `158.0.8127.89` (and read-only inspection of Microsoft Edge on the same host) established five concrete facts:

1. **`browser.theme` and `extensions.theme` are outside `Secure Preferences`**: In `%LOCALAPPDATA%\Google\Chrome\User Data\Default`, neither `browser.theme` nor `extensions.theme` appears in `Secure Preferences` or `protection.macs` (which tracks `extensions.install`, `extensions.settings`, `extensions.ui`, and `browser.show_home_button`), so offline edits to `Preferences` do not trigger HMAC tampering resets.
2. **Exact native GM3 schema in `Preferences`**: Chrome persists its native Material 3 dynamic theme via `browser.theme.color_scheme2 = 0` (`kSystem`, hot-switching immediately when Windows Light/Dark app mode toggles), `browser.theme.color_variant2 = 1` (`kTonalSpot`), `browser.theme.follows_system_colors = false`, `browser.theme.user_color2` as a signed 32-bit ARGB integer (`static_cast<int>(0xFFRRGGBB)`, e.g. `#22C55E` -> `-14498466`, `#7C3AED` -> `-8635667`, `#FE5722` -> `-108766`), and `extensions.theme.id = "user_color_theme_id"` (clearing `extensions.theme.pack`, `browser.theme.is_grayscale2`, and `autogenerated.theme.color`).
3. **Chrome Sync boundary**: When Chrome Sync holds an explicit UI-chosen `user_color` (`saved_local_theme` / `ThemeSpecifics`), `ThemeSyncableService` overwrites offline `user_color2` edits upon startup. Once Sync is on the default theme (or theme sync is turned off), Chrome loads offline `Preferences` via `InitFromPrefs()` without pushing it back to Sync, so consecutive offline seed changes (verified green -> purple across restarts) persist cleanly alongside live OS Light/Dark hot-switching.
4. **Variant and appearance trade-offs**: `kNeutral` (`color_variant2 = 2`) produces near-monochrome output; `follows_system_colors = true` inherits Windows accent/title-bar coloration with jarring surface contrast; `kTonalSpot` (`color_variant2 = 1`) preserves clear seed hue and balanced Light/Dark hot-switching. Chrome's Material 3 color mixer derives the full UI palette from one seed without per-field 24-color control or One-Tone `7:1` verification.
5. **Other Chromium browsers diverge**: Local inspection of Microsoft Edge (`%LOCALAPPDATA%\Microsoft\Edge\User Data\Default\Preferences`) showed Edge-specific keys (`mai_ds_default_theme_type`, `default_blue_theme_enrolled`, `recent_theme_color_list`, `available_dark_theme_options`) with empty `browser.theme`. Guessing compatibility across untested Chromium browsers (Edge, Brave, Vivaldi, Opera) violates One-Tone's evidence boundary.

## Decision

1. **Replace dual MV3 Chrome theme packages completely with native `Preferences` updates**:
   - Remove all MV3 theme directory/ZIP generation (`build_chrome_theme`, `build_chrome_theme_directory`, `CHROME_COLOR_ROLES`, `CHROME_TINT_ROLES`, and `chrome_activation: "manual"`), with no legacy extension-rollback compatibility branch.
   - Write the raw `Seed Color` (`plan.seed_color`) encoded as a signed 32-bit ARGB integer to `browser.theme.user_color2`, alongside `color_scheme2 = 0`, `color_variant2 = 1` (`kTonalSpot`), `follows_system_colors = false`, and `extensions.theme.id = "user_color_theme_id"`, while removing conflicting overrides (`browser.theme.is_grayscale2`, `extensions.theme.pack`, `autogenerated.theme.color`).
2. **Scope to Google Chrome Windows desktop (`verified-chrome-preferences-v1`) and single active Profile**:
   - Support Windows Google Chrome only (`chrome` Target); do not guess or touch Edge, Brave, Vivaldi, or Opera unless independently verified and added as separate Targets.
   - Resolve and freeze one `Active Target instance` during Preview by deterministic precedence: (1) `ONE_TONE_CHROME_PREFERENCES`, (2) `%LOCALAPPDATA%\Google\Chrome\User Data\Local State` `profile.last_used` (validated as a safe single-segment component), (3) `Default\Preferences`. Missing, uninitialized, symlink/junction-redirected, or structurally invalid files report `skipped` without fabricating `Preferences`. `load_plan()` requires the frozen `chrome` instance whenever `chrome` is targeted.
3. **Apply `Live-process write guard` and field-level Snapshot / Rollback**:
   - Never terminate user `chrome.exe` processes or touch `Secure Preferences` or `Sync Data/LevelDB`.
   - Reuse the fail-closed Win32 `chrome.exe` process check both at entry and immediately before `os.replace` (with unredirected-path and pre-replace byte-digest continuity checks): `Apply` returns `skipped` (`changed = false`) when Chrome is running or process enumeration fails, and `Rollback` fails closed (`failed`).
   - Snapshot records the authoritative `preferences_path`, `snapshot_sha256`, container existence flags, and exact pre-apply presence/value for the 8 managed keys (`chrome-state.json` + backup copy). Rollback restores only those 8 managed keys and removes newly created empty containers, preserving bookmarks, extensions, and other settings added after Apply.
4. **Honest status, Sync caveat, and `APPEARANCE_POLICY` bump (`2026-11-24.v10`)**:
   - Report `ok` when all 8 managed fields verify (with `rendering_verification = "untested"` and explicit `Seed-driven native theme` semantics).
   - Continue writing `Preferences` even when Sync indicators (`saved_local_theme` or `account_values`) are present, surfacing `sync_caveat = true` and advising users to reset to the default Chrome theme once in Customize Chrome (or disable theme sync) if cloud sync reverts an older UI-chosen theme.
   - Bump `APPEARANCE_POLICY` revision to `2026-11-24.v10` (replacing `chrome_activation = "manual"` with `chrome = "native_preferences_system_following_tonal_spot"`).

## Consequences

- Chrome follows Windows Light/Dark app mode switches natively and instantaneously with a single `sync` and no manual `chrome://extensions` loading or mode swapping.
- One-Tone no longer controls or verifies Chrome's individual 24 surface/text colors (`Seed-driven native theme`), and Apply/Rollback require Chrome to be closed beforehand.
- Older `v9` and earlier Plans require fresh Preview; legacy MV3 plugin artifacts must be removed manually if previously loaded.

## Rejected Alternatives

- **Retaining dual MV3 theme extensions**: rejected because static manifest themes cannot follow system Light/Dark switches without manual user intervention.
- **Using `browser.theme.follows_system_colors = true` only**: rejected because coupling Chrome to Windows Shell accents produced overly saturated/poorly layered surfaces in user testing and cannot customize Chrome independently.
- **Setting Windows Registry policy `BrowserThemeColor` / `BrowserColorScheme`**: rejected because policy enforcement displays Chrome's "Managed by your organization" notice and locks the user's Customize Chrome UI.
- **Mutating Chrome's binary `Sync Data/LevelDB`**: rejected as unsafe and fragile internal storage manipulation.
- **Applying Chrome keys blindly to Edge or Brave**: rejected because Edge uses distinct preference keys and untested Chromium browsers require independent evidence as separate Targets.
